## 1. Bruno importer: `req.setHeader(...)` translated with broken argument shape

**Repo:** `VoidenHQ/plugin-bruno-importer` (`plugins/bruno-importer` in the voiden monorepo checkout) — branch `main`
**File:** `src/utils/scriptTranslator.ts`
**Status:** Fixed locally, **not committed** — pending review

**What was wrong:** `req.setHeader(name, value)` (two positional args) was translated by a plain prefix swap into `voiden.request.headers.push(name, value)` — but `.push()` expects one `{key, value}` object, since `voiden.request.headers` is an array. The generated script silently did nothing.

**Fix:** Added `translateSetHeaderCalls()` — a depth-and-string-aware scanner that finds each call's real argument boundary (so a value like `String(Date.now())` isn't cut off early) and rebuilds it as `voiden.request.headers.push({ key: name, value: value })`.

**Also fixed in the same pass:** `req.getHeader(name)` was translated to `voiden.request.headers[name]` — but request headers are an array, not a map, so this always returned `undefined`. Changed to `voiden.request.headers.find(h => h.key === name)?.value`.

**Verified:** `tsc --noEmit` clean; compiled and ran the real `translateBruScript()` against the exact reported input — confirmed correct output.

## 2. All four importers (OpenAPI, Postman, Bruno, Insomnia): headers/query/path/multipart/url tables corrupted on generation

**Reported as:** "we updated the table to include a extra column at first for disabling and enabling, causing corruption in openapi, postman, bruno and insomnia."

**Actual root cause (not quite the hypothesis, but the symptom was 100% real):**
Not an extra column — a **literal empty string (`""`) landing in a table cell's text value**. The editor's ProseMirror engine rejects an empty text node outright, and its fallback for that is to silently discard the *whole block* the next time the file is opened — exactly the "corrupts" symptom reported, and it hits headers/query/path/multipart tables specifically because those are exactly the tables built from source data (a Postman/Bruno/Insomnia param, an OpenAPI schema) that frequently has no value set — a very common, not edge-case, situation. Every one of the four importers had at least one place where a missing value's fallback was `""`/`''`/`?? ''` instead of a real placeholder.

**Repos, files, and what changed** (all repos are separate git checkouts under `voiden/plugins/*`):

| Plugin repo | File(s) | What was wrong |
|---|---|---|
| `plugin-openapi-import` | `src/utils/converter.ts` | Hand-rolled the table JSON directly instead of using the shared, correct `voiden-rest-api` helper — and its own `tableValueFromSchema()` returned `""` for any parameter with no `schema.default` (the common case — OpenAPI parameters describe shape, not a value to send). Switched headers/query/multipart/url-table building to the shared `helpers.createHeadersTableNode()` etc., added a real 3rd (Description) column sourced from the parameter/property's own `.description` when present, and made every "no value" fallback `"—"` instead of `""`. Also removed the now-dead `toRows()` helper this replaced. |
| `plugin-postman-import` | `src/utils/converter.ts`, `src/utils/types.ts` | `makeTextCell()` — the shared cell builder every table row goes through — produced an empty paragraph for a falsy value; fixed centrally there. Separately, `helpers.createHeadersTableNode`/`createQueryTableNode`/`createUrlTableNode`/`createMultipartTableNode` were called with raw, unguarded `h.value`/`q.value`/`f.value` (bypassing `makeTextCell` entirely). `withOptionalDescriptions()` also left a per-row `""` description in place for any row without one, on a table where at least one *other* row did have one. `extractPostmanPathParams()`'s inferred-`:name`-segment fallback was `['', '']` — value **and** description empty, *every single time* a path param wasn important without Postman's explicit `variable` array populated. |
| `plugin-bruno-importer` | `src/utils/converter.ts`, `src/utils/openCollectionConverter.ts` | Same pattern, duplicated across both the classic `.bru` path (`converter.ts`) and the OpenCollection-format path (`openCollectionConverter.ts`) — headers/path/query/multipart/url-table builders all passed raw `h.value`/`p.value`/`f.value` straight to the shared helpers with no fallback, and `deriveQueryParamsFromUrl()` (also duplicated in both files) passed through a flag-style query param's (`?verbose=`) genuinely-empty value unguarded. (Bruno's own `makeTextCell` in `blockBuilders.ts`/`converter.ts` already had a safe `'n/a'` fallback — that path was already fine, confirmed by tracing it rather than assumed.) |
| `plugin-insomnia-importer` | `src/utils/converter.ts` | `convertAuthToHeaders()`'s apiKey-auth header value, the merged headers array, the query-param array, and the multipart array all had unguarded `?? ''`/no fallback. Worst instance: **every path param row was `[name, '']` unconditionally** — Insomnia carries no path-variable-value array at all, so this fired on literally every path param import, no exception. |

**Fix pattern, consistently applied:** every place a table cell's value could end up "" now falls back to `"—"` instead — the same placeholder character the base `voiden` skill's own docs recommend for a genuinely-empty cell (`row: ["—", ...]` note in its "Never write a table cell... as a literal empty string" rule).

**Verified:** all four plugins pass `tsc --noEmit` cleanly on the changed files. `openapi-import`'s two pure functions (`tableValueFromSchema`, `flattenSchemaToRows`) additionally verified at runtime with a standalone script against a real-shaped schema — confirmed `"—"` where a value/description is missing, real values passed through correctly otherwise.

## 3. Same empty-text-value bug, extended to non-table URL content (bruno-importer)

Follow-up to #2's "flagged, not fixed" note. Re-examined the base `voiden` skill's actual rule text — it says "never write a table cell **or text value** as a literal empty string," not "table cell" alone, and `surl`/`url` node `content` is exactly that: a plain text value, same rejection risk as a table cell. So this was a real instance of the same bug, not just a defensive guess.

**Repo:** `VoidenHQ/plugin-bruno-importer` — branch `main`
**Files:** `src/utils/converter.ts`, `src/utils/openCollectionConverter.ts`
**Status:** Fixed locally, **not committed** — pending review

**What was wrong:** six call sites (three per file — classic `.bru` path and OpenCollection path each have their own copy) built a gRPC/WebSocket/HTTP request's URL with `data.grpc.url ?? ''` / `data.ws.url ?? ''` / `http.url ?? ''` / `gql.url ?? ''` / `item.websocket.url ?? ''` — if the source request genuinely had no URL, that empty string became the `surl`/`url` node's literal content.

**Fix:** every one of those six changed from `?? ''` to `|| '—'`. Confirmed each fallback only ever feeds into the actual rendered URL content (or into string-processing functions — `stripQueryString`, `convertColonPathParams` — that pass a non-URL-shaped string like `'—'` through harmlessly, verified by reading each function). Left the *other*, separate `http.url ?? ''` occurrences that feed `deriveQueryParamsFromUrl` (query-string parsing only, never rendered) untouched — that usage was already safe with an empty string.

**Checked but not changed:** `openapi-import`'s `doc.servers?.[0]?.url || ""` (in `firstServer()`) looked like the same risk at first, but isn't — its result is always concatenated with `ep.path` (`${firstServer(doc)}${ep.path}`), and an OpenAPI path key is structurally guaranteed non-empty (paths are the `paths` object's own keys, always starting with `/`), so the final URL content can never actually end up empty even if `servers` is missing entirely. Verified this reasoning by reading the call site rather than assuming.

**Verified:** `tsc --noEmit` clean on both changed files.

## 4. openapi-import: path parameters silently dropped (missing feature, not corruption)

Follow-up to #2's "also found, not fixed" note.

**Repo:** `VoidenHQ/plugin-openapi-import` — branch `main`
**File:** `src/utils/converter.ts`
**Status:** Fixed locally, **not committed** — pending review

**What was wrong:** every OpenAPI operation's `in: "path"` parameters were never turned into a `path-table` block at all — not a corruption bug, just a gap. A request for `/users/{id}` imported with no path-table, `{id}` left for the person to notice and fill in blind.

**Fix:** added a PATH PARAMETERS section (positioned after query, before the request body, matching the base skill's documented block order: `headers-table → query-table → path-table → body`), mapping each `in: "path"` parameter through the same `tableValueFromSchema()` / `.description || "—"` treatment already used for headers and query, then `helpers.createPathParamsTableNode(...)`.

**Verified:** `tsc --noEmit` clean. Logic verified at runtime with a standalone script against a two-parameter example (one with a schema default, one without, one with a description, one without) — confirmed correct `[name, value, description]` rows, `"—"` only where genuinely nothing exists.
